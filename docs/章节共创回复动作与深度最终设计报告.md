# 章节共创回复动作与深度最终设计报告

## 结论

DuGNan/Moqi#144 的产品与后端设计已经定稿。当前开发中的唯一新任务策略为 `chapter-reply-policy-v5`；V5 尚处于本 Issue 调试阶段，不因每次措辞优化继续制造 V6、V7。V1–V4 只用于兼容数据库中已经存在的旧任务、重试和恢复，不代表同时维护多套当前风格。

本报告只描述当前有效设计，不记录旧 Prompt、旧 Task 或旧验收结论。最终实现是否通过，以本次最新构建重新生成的测试和验收目录为准。

## 一个回复由两个维度组成

- 讨论动作决定“本轮做什么”。
- 回复深度决定“完成这件事时覆盖多少信息”。

“总结”是动作，不是深度；“深入”是深度，不是动作。两者自由组合，系统不会因为执行总结而跳成深入，也不会因为选择深入而增加候选数量。

| 讨论动作 | 内部值 | 职责 |
|---|---|---|
| 继续讨论 | `EXPLORE` | 沿当前想法讨论、推演，或按作者要求提供候选 |
| 必要澄清 | `CLARIFY` | 只确认一个会实质改变回答的关键歧义 |
| 比较方向 | `COMPARE` | 比较对话中实际存在的对象 |
| 总结收束 | `CONVERGE` | 完整保留当前上下文中有效的决定、候选、纠正、否定和待决 |
| 章节规划 | `PLAN` | 整理请求范围内的章纲或场景规划 |
| 正文草稿 | `DRAFT` | 生成请求范围内的正文草稿 |

| 回复深度 | 内部值 | 含义 |
|---|---|---|
| 简洁 | `BRIEF` | 压缩表达，只保留完成当前动作所需的信息 |
| 平衡 | `BALANCED` | 说明主要理由、影响或取舍，足够后收束 |
| 深入 | `DEEP` | 在同一动作和范围内完整推演关系、风险和长期影响 |

例如，作者说“总结本次会话”并选择简洁，结果就是 `CONVERGE + BRIEF`：总结仍完整覆盖有效事项，但使用更紧凑的表达，不会改成深入。完整性优先于压缩程度。

## 自动深度如何确定

自动深度由后端确定性规则解析，不增加一次模型分类调用。优先级为：

1. 作者最新消息中的明确深度要求。
2. 本轮深度选择器的手动值。
3. 直接回答同一条必要澄清时，恢复澄清前暂存的目标深度。
4. 当前请求的高置信自动判断。
5. 会话、章节、作品、用户层级的继承偏好。
6. 无法可靠判断时使用平衡。

“不要深入”表示排除深入，不等于要求简洁；“不要简略”也不等于要求深入。只有排除而没有指定目标时使用平衡。同一对象前后改口时，以最后一次明确措辞为准；不同对象分别要求不同深度时，局部要求全部保留，任务记录其中最高深度用于预算和审计。

高置信自动判断只覆盖少量边界：

- 纯局部事实纠正且不重建影响：简洁。
- 明确要求完整分析多个相互影响的维度：深入。
- “写一句开场正文”：简洁；“写一段正文草稿”：无额外信号时平衡；“详细写完整场景”：深入。
- 其他情况不猜测，使用继承偏好或平衡。

## 动作与深度的特殊边界

### 局部事实纠正

只有“纠正这一事实，不重建影响”进入 `fact_correction` 专用分支。作者的更正只出现在 USER 消息；任务 SYSTEM 不复制具体事实。最终保存的回复只有更正后的事实，不追加“已确认”“其余不变”。

作者要求根据更正重新分析影响时，退出专用分支，按普通 `EXPLORE` 处理；更正仍只从 USER 消息读取。

### 必要澄清

澄清轮的实际采用深度固定为简洁，因为信息不足时不能提前展开。澄清前原本要执行的平衡或深入深度单独暂存。作者通过同一开放问题直接回答、且这仍是该问题的第一条有效回答时，下一轮恢复暂存深度；作者改谈其他动作或主题时丢弃暂存值。

### 候选与比较

深入不增加候选数量。“没有思路，请给三个方向”仍可使用平衡深度并返回三个方向；“沿第二个方向深入”只推演该方向，不在结尾附送其他方向或结局。深入把作者已经给出的事实视为封闭前提集，只允许复述前提、连接前提或标明缺口，不给前提新增性质、例子、人物行为、发生过程或额外后果；缺少依据的连接保持未知。

比较对象和数量由同一次生成模型根据作者消息和历史对话识别。前端和后端不再维护一套对象数量正则，也不增加分类调用：

- 能识别 2–5 个对象：生成相应方向卡片。
- 无法可靠识别：同一次调用可以退回一次必要澄清。
- 超过 5 个对象：返回完整可读比较，不生成控件，也不遗漏对象。
- 语义 JSON 可读但不满足控件约束：保留完整可读内容并记录降级原因。
- JSON 已损坏且无法安全恢复：任务失败，不把原始 JSON 显示给作者。

比较必须保留作者已经写明的永久、不可逆、否定和未知边界。正文、说明和取舍同样只允许复述前提、对照前提或标明缺口；某个比较维度缺少资料时，直接说明它取决于后续设定，不用人物行动、心理状态、能力表现、交易规则、恢复条件或其他新机制填满维度。

## 为什么澄清和比较使用 JSON

只有 `CLARIFY` 和 `COMPARE` 需要前端展示可回答的问题或方向卡片，因此模型生成最小中文语义草稿：

- 澄清：`回复`、`问题`。
- 比较：`回复`、`问题`、`选项`，选项内为`标题`、`说明`、`取舍`。

JSON 只是 Provider 与服务端之间的传输外壳。`schemaVersion`、控件类型、`questionId`、`optionId`、`allowCustom` 均由服务端确定性生成，不进入模型 Prompt。普通总结没有交互控件，使用普通文本，不要求 JSON。

## 总结的完整性

总结首先保留作者要求范围内的全部有效事项，其次才按简洁、平衡或深入调整表达：

- 简洁压缩措辞，不删除事项。
- 平衡补充直接关系。
- 深入解释已有事项之间的共同效果，但不补造背景、机制、证据或过程。
- 作者原有的否定和不确定措辞必须保留。
- 作者明确缩小总结范围时，只总结该范围。
- 多项内容分行或分段呈现，不能为了压缩把项目首尾粘连在一起。

V5 总结的输出预算随当前会话消息数量增长，但记录的深度不改变。Provider 以 `length` 或 `max_tokens` 结束时，整轮失败，不保存可能遗漏内容的半截总结。

这里保证的是“实际绑定进本次 Provider 上下文的有效事项”。被长上下文裁剪掉的更早历史不会被假装已经总结；跨裁剪边界的长期记忆、检索和全历史摘要属于 Issue #169。

## Prompt 与上下文边界

模型消息保持以下职责：

1. 全局 SYSTEM 只出现一次身份：“你是墨契，作者的小说共创搭档。”
2. 任务 SYSTEM 只写动作、深度、范围和必要的输出语义，不重复身份或“【必须遵守的规则】”。
3. 作品、章节正文、相关章节资料和作者已确认共识使用各自正确的自然中文来源标签。
4. 历史 USER/ASSISTANT 只依靠原生角色区分，不添加“助手先前建议”等包装。
5. 最新作者消息作为最终 USER 完整保留。

模型可见 Prompt 不出现 `primaryIntent`、`allowedChanges`、`maxCandidates`、`schemaVersion`、`single_choice`、`open_question`、`questionId`、`optionId`、`allowCustom`、权威状态码、机械字数目标或固定问号数量。

## 任务输入与兼容

新任务在 `ai_tasks.task_input_json` 中保存解析后的动作、深度、范围、控制来源、`chapter-reply-policy-v5`，以及必要澄清的暂存深度。这里保存的是结构化执行参数，不是每次复制一份完整 Prompt 文本。

新任务使用当前 V5 编译器；旧 V1–V4 任务、失败重试和取消恢复继续使用原任务中的策略与 Story Context 快照。未知动作、深度、范围或缺失自然语言映射会在 Provider 调用前失败。
