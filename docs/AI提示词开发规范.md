# Moqi 后端 AI 提示词开发规范

## 一、适用范围

本规范适用于 `moqi-backend` 中所有最终会形成大模型请求的代码，包括提示词模板、任务运行器、上下文编译器、消息组装器、Agent 指令、结构化输出契约和生成后修订流程。

本规范约束的是实际发送给 Provider 的完整消息，不仅是代码中的某一个模板字符串。

## 二、核心原则

1. 程序内部可以使用稳定的英文枚举、字段名和状态码；发送给大模型前，必须转换成清楚、具体、可执行的自然语言。
2. 不了解后端代码的产品、设计或编辑人员，应当能够直接读懂模型收到的任务、上下文、权限边界和输出要求。
3. 不以“大模型可能猜得懂”作为验收标准。未解释的内部术语进入模型请求，应视为提示词编译缺陷。
4. 提示词只保留模型完成任务真正需要的信息。仅用于数据库关联、路由、监控、审计或调试的数据不得进入模型可见文本。
5. 作者确认的事实、作者最新表达、历史讨论和助手候选建议必须保持清楚的权威边界。

## 三、内部数据与模型文本的边界

以下内容可以存在于 Java 对象、数据库、日志字段和测试数据中，但不得未经转换直接承担模型指令：

- 枚举和值，例如 `explore_direction`、`discussion_expansion`、`changes_only`。
- 字段和对象路径，例如 `replyScope.maxCandidates`、`sourceType`、`contextSnapshotId`。
- 权威状态码，例如 `confirmed`、`evidence`、`pending`、`negated`。
- 类名、方法名、表名、列名、任务编号、哈希和路由代码。
- 仅用于机器解析的 JSON 字段名和调试标记。

进入提示词编译层后，应当转换成直接说明模型行为的中文。例如：

```text
以下内容已经由作者明确确定，必须遵守。
```

```text
以下是此前的讨论。作者的表达可以用于判断意图；助手提出的内容只是备选想法，不能视为作者已经确定。
```

```text
本轮需要打开思路。作者没有指定精确数量时，给出三至五个实质不同的方向；作者指定数量时严格遵守。
```

不得把同一语义写成：

```text
【权威状态：confirmed】
primaryIntent=explore_direction
allowedChanges=discussion_expansion
maxCandidates=3
```

## 四、提示词编译职责

提示词编译层必须依次完成：

1. 读取内部状态和上下文条目。
2. 解析当前任务、作者意图、确认内容、排除内容和可修改范围。
3. 将内部状态映射为自然语言任务说明。
4. 删除模型不需要的字段名、状态码和调试信息。
5. 按正确角色组成 `system`、`user`、`assistant` 消息。
6. 生成不可变请求快照，供测试、审计和问题复现使用。

内部枚举到自然语言的映射必须显式、完整且可测试。出现未支持的新枚举时，应阻止请求并暴露开发错误，不得把原始值透传给模型，也不得静默降级成含义不同的默认行为。

## 五、角色与历史对话

1. 作者原话使用 `user` 角色，Moqi 的历史回复使用 `assistant` 角色，规则和作品级说明使用 `system` 角色。
2. 不得把一组“用户说了什么、助手回复了什么”合并成单条 `user` 消息，再依靠“证据”“权威状态”等包装词要求模型自行还原角色。
3. 历史助手回复只能作为候选建议和讨论线索，不能升级成作者已经确认的事实。
4. 作者最新消息优先于历史讨论；明确否定、改选或纠正必须覆盖旧建议。
5. 被上下文窗口裁剪的历史仍应保持完整的用户—助手轮次，不得留下无法识别来源的半条消息。

`system`、`user`、`assistant` 是 Provider 协议角色，不属于需要删除的程序黑话；但每条消息的正文仍必须符合本规范。

## 六、行为规则的自然语言表达

行为要求必须说明模型要做什么，而不是只提供抽象标签。例如：

- 直接回答：解释当前问题的核心原因、区别和适用边界，不顺带扩写未询问的故事方案。
- 发散探索：打开设计空间，提供若干实质不同的方向，并说明价值与风险。
- 比较多个方向：尊重作者指定数量；未指定时以有效差异为先，不使用同义改写凑数。
- 沿选定方向深化：只在作者已经选择的方向内部补足因果、落点和风险，不重新发散。
- 澄清关键歧义：只有无法从上下文确定关键指代，且不同解释会实质改变回复时才追问。

这些中文名称是提示词文案，不要求与代码枚举同名。代码负责稳定识别，提示词负责让模型准确执行。

## 七、回复深度与约束

1. 回复深度描述信息覆盖程度，不等同于固定字数。
2. 深入讨论应增加当前问题内部的因果、取舍、风险和落地信息，不得借深度扩大任务范围。
3. 不设置无业务依据的最小字符数，不为了达到篇幅重复结论或补造设定。
4. `max_tokens` 是 Provider 安全上限，不得在提示词中描述成创作目标。
5. “最多向作者提出一个需要回答的问题”约束的是交互负担，不等同于机械限制全文只能出现一个问号。
6. 能由程序准确检查的规则，应优先在生成后校验；需要修订时，只根据明确证据做一次最小必要修订，不进行开放式重写。

## 八、结构化输出例外

当模型输出确实由程序解析时，可以使用 JSON、固定字段或固定分类值，但必须满足：

1. 用自然语言解释任务和每个允许值的含义。
2. 只暴露完成该协议所需的字段。
3. 结构化协议不得混入面向作者的共创回复提示词。
4. 解析失败必须有明确错误和重试边界，不得把错误结构当作正常创作内容展示。

技术问答本身需要讨论 API、代码字段或数据库时，可以保留相关技术名词；这不构成内部实现泄漏。

## 九、测试与验收

新增或修改提示词编译逻辑时，必须验证实际发送给 Provider 的完整消息快照，而不是只检查模板或根据代码推测请求。

至少覆盖：

- 短上下文与达到裁剪上限的长上下文。
- 作者无思路、要求多个候选、明确指定数量、选定方向、否定旧方向和纠正助手。
- 已确认内容、候选建议、待决内容和已否定内容同时存在。
- 适中讨论与深入讨论。
- 未知枚举、缺失映射和结构化输出解析失败。

每次验收必须检查：

1. 实际消息正文不存在未解释的内部枚举、字段名、状态码或路由代码。
2. 作者与助手历史消息角色正确。
3. 作者确认事实和助手候选建议没有混用。
4. 当前任务、允许范围、禁止范围和回复深度使用自然语言表达。
5. 动态规则之间不存在冲突，例如同时要求发散并禁止多个候选。
6. 作者明确数量得到遵守；作者没有明确数量时没有伪造精确要求。
7. 真实模型回复完成了本轮任务，没有宣称内容已经保存或确认。

黑话扫描只能作为辅助检查，不能替代完整快照阅读。仅维护一份禁止词列表也不足以发现新枚举泄漏，必须同时测试映射完整性和未知值失败行为。

## 十、安全与观测

1. 提示词快照、测试报告和日志不得包含 API Key、Token、密码或其他凭据。
2. 用户正文和长篇模型输出不得无条件写入普通运行日志。
3. 调试导出应存放在规定的本地 QA 目录，不得直接提交包含真实用户隐私的原始数据。
4. 观测字段可以记录枚举、任务编号和哈希，但必须与模型可见消息正文分开保存。

## 十一、代码评审清单

凡是新增或修改提示词相关代码，评审必须同时查看：

1. 内部状态到自然语言的映射实现。
2. 未知值和缺失映射的失败方式。
3. 一个短上下文和一个长上下文的完整请求快照。
4. 提示词黑话扫描与角色顺序检查结果。
5. 至少一组真实模型回复。
6. 作者确认、否定、改选、无思路和指定候选数量等边界样例。
7. 能否由不了解代码的人员准确复述每段提示词的作用。

发现内部字段未经转换进入模型消息时，应按提示词编译缺陷处理，而不是作为文案风格问题忽略。
