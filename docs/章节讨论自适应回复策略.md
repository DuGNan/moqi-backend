# 章节讨论自适应回复策略

## 适用范围

本文描述 `conversation_reply` 任务的当前后端策略、偏好优先级、任务快照和 Story Context 权威边界。前端控件、共识成熟度自动触发、正式章纲和场景规划契约不在当前范围。

## 回复策略

`replyMode`（回复模式）固定为：

- `explore`（开放共创）：默认模式。先综合作者输入，再从因果、人物动机、冲突或叙事后果中拓展一两个有价值的方向。
- `clarify`（澄清）：仅在会阻断当前章节方向的高影响歧义时，一次只问一个关键问题。
- `compare`（比较）：仅在用户明确索要候选、比较方案或明确表示没有思路时给出 2 至 4 个候选，同时允许自由描述。
- `converge`（收束）：只总结已确认内容和剩余待决，不扩写新设定。
- `plan`（规划）：仅在用户明确请求章纲、场景或章节设计时输出结构化规划，不生成正文。
- `draft`（草稿）：仅在用户明确请求正文或片段时生成草稿。

`replyDepth`（回复深度）固定为 `brief`（简洁）、`balanced`（平衡）和 `deep`（深入）。开放共创默认 `balanced`，澄清与比较默认 `brief`；明确规划默认 `balanced`；明确正文默认 `deep`。用户表达“太多”“复杂”“改动太大”时，本轮按 `converge/brief` 收敛。

普通讨论默认只处理一个主要意图。局部要求使用 `changes_only`，不重新输出完整世界观或整章方案；“继续展开”可以增加深度，但不扩大已限定的 `replyScope`（本轮推进范围）。

上一轮刚澄清或给出选项、用户只作短答时，新任务快照记录最近模式和“抑制连续出题”结果，本轮强制回到 `explore`。除非用户明确要求跨章讨论，Prompt 只允许处理当前章节；不得主动设计下一章、输出未经请求的“我的倾向”或用连续二选一替代共同思考。

## 控制优先级

有效深度按以下顺序解析：

`单次 replyControl > conversation > chapter > work > user > system`

消息请求可选增加：

```json
{
  "replyControl": {
    "depth": "auto",
    "scopeMode": "current_only",
    "scopeText": "只讨论第一章觉醒方式"
  }
}
```

`depth` 支持 `auto/brief/balanced/deep`，`scopeMode` 支持 `auto/current_only`。旧客户端不提交 `replyControl` 时保持兼容。

偏好接口：

- `GET /api/reply-policy/preferences?scopeType=conversation&scopeId=123`
- `PUT /api/reply-policy/preferences`

保存请求包含 `scopeType`、`scopeId`、`replyDepth` 和更新已有记录时必填的 `baseVersion`。当前单用户版本将用户标识固定为 `local-user`；服务端仍会验证 work、chapter、conversation 资源真实存在，不能用客户端文本替代资源归属。

## 任务快照与重试

创建消息和 AI task 的同一事务中，服务端解析并写入 `ConversationReplyTaskInputV1`：

- `messageId`、`conversationId`
- `replyMode`、`replyDepth`、`replyScope`
- `controlSource`
- `policyVersion`
- `contextAuthorityVersion`
- `convergenceApplied`
- `previousReplyMode`、`consecutiveQuestionSuppressed`、`crossChapterRequested`

Runner 只消费该快照。失败重试复用原 `ai_tasks.task_input_json`，偏好后来变化不会静默改变旧任务语义。历史无快照任务可按兼容默认规则执行；新任务快照不保存消息正文、完整 Prompt 或隐藏推理。

## 结构化讨论交互

`compare` 和必要的 `clarify` 请求模型输出 JSON；服务端校验后把可读正文与 `interaction` 分开持久化。当前支持 `single_choice` 和 `open_question`，单选包含 2 至 4 个唯一选项，始终保留作者自定义描述入口。模型结构无效时只保留普通文本，不把未校验 JSON 暴露为可操作控件。

用户提交结构化回答时必须通过 `referencedMessageId` 引用同一章节、同一会话的来源助手消息。服务端校验 `questionId` 和 `optionId` 归属，生成可读用户消息正文，并把原始结构化回答保存到 `interaction_response_json`。结构化选择只创建新讨论消息与来源证据，不确认或修改 Brief、章纲、场景规划、正文或作品资料。

`GET /api/ai-tasks/{taskId}` 对 `conversation_reply` 返回由该快照解析的 `effectiveReplyPolicy`。前端应只展示这个服务端最终结果，不在客户端重复推断优先级或模式。

## 权威上下文

Story Context 快照 schema 为 V2，每个 `StoryContextItem` 增加 `authorityStatus`：

- `confirmed`（已确认）：confirmed Brief、confirmed 正式大纲和确认知识，可作为权威事实。
- `candidate`（候选）：仅在当前讨论焦点相关时装配，不得自动升级。
- `pending`（待决）：当前待决焦点或未解决伏笔，不得当作事实。
- `rejected`（已否定）：只保留不含原文的短墓碑，禁止继续继承。
- `evidence`（证据）：历史讨论和当前用户输入，只用于理解，不得覆盖 confirmed。

旧快照缺失 `authorityStatus` 时按 `evidence` 安全降级。普通章节讨论不再把 draft Brief 或 draft 大纲当作普通事实装入；其他 Story Context profile 继续使用相同来源与预算机制。

## Prompt、预算与审计

Task Rule 由 `replyMode/replyDepth/replyScope` 稳定生成，明确：

- `plan` 不等于 `draft`；
- 普通讨论一次一个主要意图；
- 候选数量受限；
- AI 输出不能自动确认或保存 Brief、大纲、场景规划和正文。

输出 token 预算按模式和深度计算，并受 Provider 上限约束。`llm_model_calls` 对 conversation reply 记录 `ai_task_id`、`conversation_id`、模式、深度、范围安全摘要、控制来源、策略版本、token、耗时、终态和安全错误码。范围摘要不包含 `scopeText`，审计不保存完整 Prompt、隐藏推理、密钥或 Provider 原始响应。

## 固定回归

自动测试固定覆盖章节 62 暴露的 11 类输入：题材方向、能力选择、复杂反馈、含糊架空、局部架空、局部觉醒方式、完整章节设计、正文草稿、总结确认、继续展开和方案比较。同时覆盖三种深度、全部偏好优先级、旧请求/旧快照兼容、取消/失败终态和审计安全边界。
