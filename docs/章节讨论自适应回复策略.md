# 章节讨论自适应回复策略

## 适用范围

本文描述 `conversation_reply` 任务的当前后端策略、偏好优先级、任务快照和 Story Context 权威边界。前端控件、共识成熟度自动触发、正式章纲和场景规划契约不在当前范围。

## 回复策略

`replyMode`（回复模式）固定为：

- `explore`（开放共创）：默认模式。沿作者当前选择的方向继续思考；作者请求候选或明确表示没有思路时，可以在该动作内提供作者要求数量的方向，但不强制作者立即选择。作者没有请求候选时不自行改成多方向列表。
- `clarify`（澄清）：仅在不同解释会实质改变回复且上下文无法判断时提出一个必要问题。
- `compare`（比较）：仅在用户明确要求比较、对比、说明区别或判断优劣时使用。作者指定数量时遵守；未指定时比较少量实质不同的候选，同时允许自由描述。作者没有要求推荐时只说明差别和取舍，不替作者选择。
- `converge`（收束）：只总结已确认内容和剩余待决，不扩写新设定。
- `plan`（规划）：仅在用户明确请求章纲、场景或章节设计时输出结构化规划，不生成正文。
- `draft`（草稿）：仅在用户明确请求正文或片段时生成草稿。

`replyDepth`（回复深度）固定为 `brief`（简洁）、`balanced`（平衡）和 `deep`（深入）：

- 简洁直接回应作者，只保留理解答案所必需的信息。
- 平衡在直接回应的基础上，补充理解和继续判断所需的主要依据，信息充分后收束。
- 深入完整分析作者当前问题，把重要条件、发展逻辑和影响说清，并在作者要求的范围内充分展开。

回复模式与深度相互独立。比较、澄清、总结和“没有思路”不直接选择某个深度；自动模式无法高置信判断时回退平衡。只确认、撤回或纠正一个局部事实且不要求重建影响时可自动选择简洁；明确要求深入、详细、完整推演、系统分析或完整处理多个相互影响的维度时选择深入。收束信号只决定讨论动作，不会在最终阶段覆盖已经解析的深度，因此“深入总结”仍为深入。

局部事实纠正在策略快照中使用 `fact_correction` 与普通的当前焦点 `changes_only` 区分。能高置信截取时，作者本轮明确写出的更正片段会保存到现有范围引用中，供服务端校验和规范化最终结果；模型只从原始 USER 消息读取这段事实，任务 SYSTEM 不再重复作者原话。对应指令只保留“回复更正后的事实、不追加确认语或说明”这一项任务，不叠加“继续讨论”或通用深度说明。无法安全截取时使用同一简短通用指令。该过程不增加模型调用或数据库字段，重试与恢复继续复用原快照；普通当前焦点仍可按作者选择的深度讨论。这两个内部值只用于持久化和编译，不直接进入 Provider 消息。

普通讨论默认只处理一个主要意图。局部要求使用 `changes_only`，不重新输出完整世界观或整章方案；“继续展开”可以增加深度，但不扩大已限定的 `replyScope`（本轮推进范围）。

上一轮刚澄清或给出选项、用户只作短答时，新任务快照记录最近模式和“抑制连续出题”结果，本轮回到 `explore`。必要澄清本轮实际采用简洁深度，并把澄清前的非简洁目标深度记为 `deferredReplyDepth`；只有作者通过同一开放问题直接提交第一条有效回答时才恢复该深度，作者改谈其他动作或主题时不继承。除非用户明确要求跨章讨论，Prompt 只允许处理当前章节；不得主动设计下一章、输出未经请求的“我的倾向”或用连续二选一替代共同思考。

## 控制优先级

有效深度按以下顺序解析：

`作者最新消息中的明确要求 > 单次 replyControl > 同一澄清的暂存深度 > 当前请求自动规则 > conversation > chapter > work > user > 平衡回退`

显式否定不是反向档位：“不要深入”只排除深入，“不要简略”只排除简洁；没有指定剩余目标时使用平衡。同一对象前后改口时最后一条明确深度要求生效；不同对象分别指定深度时局部要求都保留，整体任务用最高深度配置预算与审计。

消息请求可选增加：

```json
{
  "replyControl": {
    "depth": "auto",
    "scopeMode": "current_only",
    "scopeText": "只讨论第一章觉醒方式"
  }
}
```

`depth` 支持 `auto/brief/balanced/deep`，`scopeMode` 支持 `auto/current_only`。旧客户端不提交 `replyControl` 时保持兼容。

偏好接口：

- `GET /api/reply-policy/preferences?scopeType=conversation&scopeId=123`
- `PUT /api/reply-policy/preferences`

保存请求包含 `scopeType`、`scopeId`、`replyDepth` 和更新已有记录时必填的 `baseVersion`。当前单用户版本将用户标识固定为 `local-user`；服务端仍会验证 work、chapter、conversation 资源真实存在，不能用客户端文本替代资源归属。

## 任务快照与重试

创建消息和 AI task 的同一事务中，服务端解析并写入 `ConversationReplyTaskInputV1`：

- `messageId`、`conversationId`
- `replyMode`、`replyDepth`、`replyScope`
- `controlSource`
- `policyVersion`
- `contextAuthorityVersion`
- `convergenceApplied`
- `previousReplyMode`、`consecutiveQuestionSuppressed`、`crossChapterRequested`
- `deferredReplyDepth`（只在必要澄清时暂存原目标深度）

新任务使用 `chapter-reply-policy-v5`。Runner 只消费该快照，不重新推断深度或候选数。失败任务仍按原语义原地恢复为 `queued`；已取消任务重试会创建新的 `queued` 子任务，复用原 `messageId`、策略与已绑定的 Story Context 快照，并通过 `retryOfTaskId` 追溯来源。恢复时只读取原快照，不按当前 Prompt 或当前资料重新构建上下文。唯一约束保证对同一已取消任务重复请求只返回同一个子任务。新任务按快照中的原始 `messageId` 读取输入，不要求再复制用户消息。偏好后来变化不会静默改变旧任务语义。历史 V1/V2/V3/V4 策略继续使用各自的兼容编译规则；历史无策略快照任务按兼容规则生成一次安全输入。新任务快照不保存消息正文、完整 Prompt 或隐藏推理。

## 结构化讨论交互

`compare` 和必要的 `clarify` 仍保留结构化交互，因为服务端需要把可读回复与前端可回答的问题或方向卡片可靠分离。模型只生成使用中文语义字段的最小 JSON 草稿：比较包含“回复、问题、选项”，每个选项包含“标题、说明、取舍”；澄清只包含“回复、问题”。Prompt 说明字段语义，不再放置要求模型照抄的完整 JSON 示例，也不固定澄清回复或问题的逐字内容。`schemaVersion`、交互类型、问题 ID、选项 ID 和是否允许自定义回答均由服务端根据任务快照确定性补齐，不进入模型消息。服务端校验后把可读正文与 `interaction` 分开持久化。比较对象和数量由同一次生成模型从作者消息及历史对话识别，不由前端、正则或额外分类调用预先计算：2 至 5 个对象生成单选卡片，无法可靠识别时同轮退回开放澄清，超过 5 个对象时保留全部可读比较但不生成控件。比较保留作者明确写出的永久、不可逆、否定和未知边界；某个维度资料不足时说明取决于后续设定，不用血统、市场、组织、偏见、阶层规则或额外能力机制填充。可读语义不满足控件约束时降级为普通文本并记录原因；JSON 已损坏且无法安全恢复时任务失败，绝不把原始 JSON 暴露给作者。

用户提交结构化回答时必须通过 `referencedMessageId` 引用同一章节、同一会话的来源助手消息。服务端校验 `questionId` 和 `optionId` 归属，生成可读用户消息正文，并把原始结构化回答保存到 `interaction_response_json`。结构化选择只创建新讨论消息与来源证据，不确认或修改 Brief、章纲、场景规划、正文或作品资料。

`GET /api/ai-tasks/{taskId}` 对 `conversation_reply` 返回由该快照解析的 `effectiveReplyPolicy`。前端应只展示这个服务端最终结果，不在客户端重复推断优先级或模式。

## 停止与部分回复

运行中任务取消先进入非终态 `canceling`，同时发布 `reply.canceling` 并请求 Provider 停止。Runner 将停止前已经对用户可见的文本与任务终态放在同一短事务中持久化：非空文本保存为 `generationStatus=stopped` 的 assistant 消息，任务随后进入 `canceled` 并设置 `resultMessageId`；没有可见增量时不创建空消息。只有上述事务完成后才发布 `reply.canceled`，其 `messageId` 可为空。排队任务无需等待 Provider，可直接进入 `canceled`。

完整生成的 assistant 消息返回 `generationStatus=completed`，普通用户消息为 `null`。消息读取结果同时返回关联任务的 `retryOfTaskId`。停止消息可查看、引用，并以明确的“不完整”标签进入后续讨论上下文；它不会启动共识成熟度流程，也不得据此自动确认候选或写入任何权威资产。

## 权威上下文

Story Context 快照 schema 为 V2，每个 `StoryContextItem` 增加 `authorityStatus`：

- `confirmed`（已确认或正式生效）：章节共识中作者已经确认的决定，以及 confirmed Brief、正式大纲和确认知识，可作为权威依据。
- `candidate`（候选）：仅在当前讨论焦点相关时装配，不得自动升级。
- `pending`（待决）：当前待决焦点或未解决伏笔，不得当作事实。
- `rejected`（已否定）：只保留不含原文的短墓碑，禁止继续继承。
- `evidence`（证据）：历史讨论和当前用户输入，只用于理解，不得覆盖 confirmed。

旧快照缺失 `authorityStatus` 时按 `evidence` 安全降级。状态码只存在于快照元数据，不直接进入模型消息。模型可见标签按来源表达：作品标题标为“当前作品”，章节正文标为“当前章节正文”，摘要和关键事件标为“相关章节资料”，confirmed Brief、正式大纲和确认知识标为“当前有效的作品资料”；只有章节共识中作者已经确认的决定标为“作者已经明确确定”。待决项和已否定内容继续以自然中文说明边界。历史消息只依靠 Provider 原生的 `user`、`assistant` 角色区分来源，不再给每条 assistant 历史添加“尚未确认”等解释性包装；已存量的同类开头提示在装配新快照时会被清除。助手回复原文仍会保留，使作者的“采用刚才那个”等指代可以还原；是否成为既定事实只由单独装配的已确认资料和作者后续明确采纳决定。普通章节讨论不把 draft Brief 或 draft 大纲当作普通事实装入；预算不足时只保留完整的作者—助手轮次。

## Prompt、预算与审计

当前版本的模型可见语言固定在 `chapter.policy.ConversationReplyPromptTemplatesV5`，按表达方式、讨论动作、回复深度、候选数量、范围、权威/会话边界和必要的语义输出草稿分组维护。墨契身份由 Story Context 的全局 SYSTEM 消息统一介绍，任务规则不重复身份或“必须遵守”包装。它不是作者配置，也不从数据库或前端热更新；`ConversationReplyPromptCompiler` 只读取任务创建时保存的结构化执行参数并选择、组合对应模板，任务输入不复制完整 Prompt。讨论回复不会把“没有保存或更新资料”重复写进 Prompt；是否写入 Brief、大纲、场景规划、正文或作品资料由应用服务和人工确认入口保证。深度模板只控制信息覆盖程度，并按当前动作选择不冲突的自然语言：必要澄清本轮采用简洁，只用对话中已有对象确认当前歧义指向，不增加对象类别，也不在同一问题里继续询问如何修改或要求新设定；深入探索只沿一个方向把作者已有前提之间的连续因果、取舍和影响说完整，不在结尾追加多个可选分支，不自行补造作者未给出的机制、事件、证据、阶段或结局，作者未说明的触发、选择、顺序、程度和可控性保持未知，也不用具体人物、事件或经历代替作者举例，不推定其他人物知情或行动；“可能”和“可以”只能标记现有前提的直接心理或关系影响，不能成为补入新前提或新过程的包装；总结先保留实际 Provider 上下文中作者要求范围内的全部有效决定、候选、纠正、否定和待决，再按深度压缩或展开，多项内容分行或分段，保留作者原有的否定与不确定措辞，不把“未知”扩写成无法验证、证据不足或其他未给出的叙事机制。跨裁剪边界的完整历史总结属于 Issue #169。

V5 在 Issue #144 完成前是当前唯一调试版本，措辞优化直接收敛到 V5，不为每次修改新增版本。历史 V1–V4 只保留兼容编译路径；旧任务、重试和恢复继续读取原任务的策略与 Story Context 快照，不重新按 V5 构建上下文。

Task Rule 明确：

- `plan` 不等于 `draft`；
- 普通讨论一次一个主要意图；
- 候选数量服从作者请求和讨论动作，不由深度决定；
- 回复使用创作搭档式的直白中文，不写成规则检查或方案评审，不使用“因果压力”“因果落点”等内部分析措辞；
- 作者明确要求新增现象、事件或设定时允许在请求范围内补充，不与通用防扩写规则冲突；
- AI 输出不能自动确认或保存 Brief、大纲、场景规划和正文。

模型可见规则只使用自然中文，不包含策略字段名、内部枚举值、权威状态码、固定字数目标或固定问号数量。`max_tokens` 只作为 Provider 安全上限。模式、深度和范围缺失或出现未知映射时，请求在进入 Provider 前失败；内部稳定值继续用于任务快照和观测。

输出 token 预算按模式和深度计算，并受 Provider 上限约束。V5 总结按当前会话消息数量增加输出预算，但不会改变已解析的深度；Provider 因 `length` 或 `max_tokens` 截断总结时任务失败，不保存不完整结果。流式增量发布和回复完成持久化都会防御性清除模型模仿出的开头候选状态提示；提示被拆分到多个流式片段时，服务端会等到能够判断前缀后再发布正文，不修改没有状态提示的正常回复。`llm_model_calls` 对 conversation reply 记录 `ai_task_id`、`conversation_id`、模式、深度、范围安全摘要、控制来源、策略版本、token、耗时、终态和安全错误码。范围摘要不包含 `scopeText`，审计不保存完整 Prompt、隐藏推理、密钥或 Provider 原始响应。

## 固定回归

自动测试覆盖显式三档、作者最新要求与继承偏好的优先级、局部纠正、纠正后重建影响、无思路、简单与多维比较、必要澄清、总结、深入总结、指定候选数量、未知映射失败、旧快照、重试与恢复。同时审计短上下文和接近输入预算的长上下文完整消息，检查角色顺序、完整轮次裁剪、权威边界、内部术语和动态规则冲突。
