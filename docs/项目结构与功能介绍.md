# 墨契后端项目结构与功能介绍

## 文档目的

这份文档用于帮助新会话、新协作者或未来回看代码的人快速理解后端项目当前的结构、功能和运行约束。
它不是一次性说明，而是随着模块、接口、数据结构和运行约束演进持续补充的后端项目介绍文档。

## 场景小说生成工作流

- `chapter.service.SceneGenerationService` 负责创建、重生成、查询、取消和步骤重试；请求只能引用本章节已发布的 ScenePlan。常规 `all` 使用 `whole_chapter_once` 一次生成整章，可选冻结当前正文或同章节同规划版本的基础候选作为参考；`continue_from` 与 `rewrite_selected` 保留逐场景兼容链。创建批次前通过 `ChapterGenerationBriefService` 编译固定版本 Brief，并把自然语言、来源引用、稳定指纹、容量结果和可选基稿冻结到 `basisSnapshotJson`；重试与恢复不会重新读取当前来源。
 - `sourcechain.ChapterAssetSourceChainService` 提供章纲、当前场景规划和最近正文批次的来源链查询；来源快照不可变，上游变化通过 `current`、`needs_review`、`superseded` 状态提示复核，不会静默改写运行中的正文批次。
- `chapter.workflow.SceneNovelGenerationWorkflowDefinition` 通过 Agent Runtime 为新全量批次执行 `load_generation -> generate_chapter -> finalize_generation`，为局部和历史批次保留逐场景与 `cohere_chapter`。`ChapterGenerationPromptCompiler` 只把冻结的人类可读 Brief、容量提示和可选基稿交给 `whole-chapter-v1`，不投放原始 ScenePlan JSON；`ChapterGenerationModelInvoker` 拒绝 JSON、Markdown、分析或 Prompt 回显，并通过 Observed Provider 保留模型调用。远程模型调用不位于数据库事务中。
- `chapter.entitycard` 按 ScenePlan 显式设定 ID、唯一名称或别名、章共识/章纲/场景文本以及上章已确认状态选择同作品 `active` 正式设定，不使用“最近 N 条”补充。实体卡保留别名、所属、故事作用、当前状态、角色认知边界、首次出现说明、禁止推断和来源版本；同名歧义只保留规划名称与禁止推断提示。`GET /api/chapters/{chapterId}/generation-entity-cards-preview` 可按可选 `scenePlanNo` 只读返回相同选择结果、固定来源和稳定指纹，不调用模型、不持久化或确认任何资产。
- `chapter.service.impl.ChapterGenerationExperimentServiceImpl` 提供与正式正文和候选完全隔离的生成策略实验：`whole_chapter_once` 将完整有序场景规划一次交给模型，`scene_then_cohere` 依次生成场景后再整章收束，`loose_story_intent` 只向模型提供一段宽松的本章故事意图，由模型自由组织时间、地点、场面和节奏。实验结果、实际输入、输入指纹、模板、模型配置、调用 ID、字数和耗时写入 `chapter_generation_experiments`，不会写入 `chapters.content` 或 `chapter_generations`。
- `chapter_generations.generated_content` 保存 `whole_chapter_once` 完整候选，`generation_model_call_id`、`generation_template_version`、`generation_finish_reason` 保存直接整章调用元数据；`chapter_generation_scenes` 与 `cohesion_*` 继续承载局部和历史兼容批次。`GET /api/chapters/{chapterId}/generations/latest-active` 以数据库和 Agent Step 恢复运行、失败或待处理候选，并公开准确的 `currentAttempt`、`retryable`；`POST /api/generations/{generationId}/retry` 只重试失败的 `generate_chapter`，历史收束仍使用 `/cohere/retry`。
- 完整正文完成后保持既有 `preview` generation 与 SSE/API 契约，由 `ChapterGenerationCompletionHandler` 自动创建独立整章评价；`whole-chapter-evaluator-v3` 在 DTO 转换前逐字段校验结构化 Finding，只执行不会扩大候选权限的单向安全规范化：收敛证据文本包装、移除整章来源中的模型场景误填和无法从来源快照验证的 Story Fact 引用，并关闭非阻塞 Finding 的模型自动修订误标；规范化字段路径保存到 Agent Step 输出。缺字段、错型、错误枚举、错误场景引用或多 Finding 中任一不安全项都会使整批安全失败；采纳服务仅接受最新整章报告的 `pass/warning`，用户仍可拒绝候选。
- `release.StoryReleaseService` 将原稿、生成稿、#106 有界修订稿和人工编辑稿固化为不可变 `chapter_prose_revisions`。正文内容、哈希、父 revision 和来源创建后不更新；评价绑定只推进 `draft/reviewing/confirmable` 状态，发布与回退必须由用户显式确认，并在单个事务中创建新的 Story Release、切换作品和全部变更章节指针。历史 release 与历史正文始终保留。
- `impact.ProseImpactService` 在正文 revision 进入发布工作区后，通过 Agent Runtime 对 Story Release 章节映射解析出的固定基线和目标正文生成结构化影响报告。输入指纹绑定 baseline release/revision 与正文哈希、目标 revision 与正文哈希、分析器版本及全作品 V24 来源图指纹；任一来源变化都将旧报告读为 `stale`。`prose-impact-analyzer-v2` 要求证据逐字引用目标正文并使用 Java UTF-16 offset；仅在证据文本唯一精确出现时有界重算 offset，不做裁剪或模糊匹配，其他形态按安全类别和 `changes[i].evidence*` 路径失败。每条事实必须提供同作品 `affectedChapterIds`：local/adjacent 受章节邻接边界约束，cross-chapter 只传播明确引用章节，work/unknown/faction-rule 进入人工处理且不自动失效全书。服务端重新校验事实类型、认知状态、置信度和影响范围；角色主张、传闻、推测、未解释现象与作者后台信息不会被提升为权威事实。报告阶段只写报告、事实变化和受影响资产，不修改正文、规划或知识权威态。
- 章节讨论回复由 `chapter.policy` 在消息创建时解析为默认开放共创 `explore`，以及必要的 `clarify/compare/converge/plan/draft` 与 `brief/balanced/deep`，并以 `ConversationReplyTaskInputV1` 写入 `ai_tasks.task_input_json`；失败重试只消费原策略快照。最近回复模式、连续出题抑制和显式跨章请求也进入快照。深度优先级为单次控制、会话、章节、作品、用户、系统，偏好通过 `/api/reply-policy/preferences` 读写。Story Context V2 将已确认、候选、待决、已否定和证据分层，旧快照缺失状态时降级为 evidence；完整规则见 `docs/章节讨论自适应回复策略.md`。
- `ChapterSseRegistry` 转发场景生成资源事件；客户端收到事件后重新读取批次或场景，不能从 SSE 获得正文、prompt 或凭据。
- 详细请求结构、状态和错误语义见 `docs/场景小说生成接口.md`；恢复和重试边界见 `docs/Agent Runtime 恢复语义.md`。

## 当前项目定位

- Moqi 后端当前承担写作主流程的数据与服务基础：作品、章节、章节共创、章节大纲/简报、章节生成、章节正文保存，以及长篇小说第一版必通知识层。
- 当前接口文档生成应以 P0 写作主流程和已落库知识层为准，不为尚未落库的增强能力生成正式接口。

## 当前模块与分层概览

- `moqi-start` 是 Spring Boot 启动模块，负责装配配置、扫描组件并承载 Flyway 迁移资源。
- `moqi-web` 是 Web 接入层，包含健康检查、作品章节、章节共创、知识层、用户配置、模型状态、AI 任务、Agent Run 和 LLM 调用观测只读查询 Controller，以及全局异常处理。
- `moqi-service` 是业务服务层，承载应用服务和领域流程编排。
- `moqi-service` 通过 Provider V2 的有序消息、通用选项、响应元数据、统一流事件、能力声明和 `LlmStreamCall` 隔离厂商协议；DeepSeek 是首个实现，Factory 与上层业务只接收供应商无关运行时配置。Provider 每次按数据库配置和最小作用域解密的凭据动态创建，不缓存包含 Key 的客户端。
- `moqi-dal` 是数据访问层，包含 MyBatis-Plus 实体与 Mapper；当前已有作品、章节、章节共创、章节生成、不可变正文 revision、Story Release、知识层和大模型凭据相关实体。
- `moqi-dal` 的持久化实体统一使用 Lombok `@Data` 生成机械方法，不重复声明 `@Getter`、`@Setter`。Lombok 仅作为编译期依赖，不参与运行时逻辑。
- `moqi-common` 是公共基础模块，包含统一响应、错误码和业务异常等跨模块基础类型。
- 所有生产与测试 Java 顶层类型均在 import 区域之后、类型级注解和声明之前维护作者、创建日期和职责说明；具体模板与填写规则以仓库根目录 `AGENTS.md` 为准。

## 构建与规范检查

- Codex 的项目级工作方式由本仓库 `AGENTS.md` 约束：标准业务开发可使用 `DgnCoding`，已有计划进入执行时可使用 `executing-plans`，重型自动循环只在用户明确要求时启用。仓库不使用项目级 `.codex/config.toml` 选择性禁用用户 Skill，避免配置语法有效但运行时未参与 Skill 过滤。
- 当前运行基线为 Java 17、Spring Boot 3.5.8、Spring AI Alibaba 1.1.2.2 和 Spring AI 1.1.2，并使用 `spring-ai-starter-model-deepseek` 对接 DeepSeek Chat 模型。
- 后端使用多模块 Maven 构建，提交前执行 `mvn clean verify` 和 `git diff --check`。
- 根 `pom.xml` 在 Maven `verify` 阶段为各 Java 模块执行 Alibaba P3C PMD 检查，检查结果写入各模块的 `target/pmd.xml`。
- P3C 当前采用报告模式，`failOnViolation=false`；规范违规会出现在 Maven 日志和报告中，但不会因此阻断编译、测试、验证或打包。
- Maven `BUILD SUCCESS` 仅表示构建和测试成功，不表示 P3C 无违规；交付时必须分别报告 Maven 结果、P3C 结果和遗留规范问题。

## 主要功能与服务说明

- 作品与章节能力：保存作品基础信息、章节标题、章节顺序、章节类型、正文和工作流状态。
- 章节共创能力：用户通过普通 POST 提交消息；当请求创建 `conversation_reply` 任务时，事务提交后由有界线程池异步调用已验证可用的 DeepSeek Provider，普通开放共创逐段产生回复事件，必要澄清和显式方案比较使用经校验的结构化交互，最终持久化 assistant 消息并将 `ai_tasks.result_message_id` 指向该消息。`chapter_conversation_messages.interaction_json` 保存助手问题，`interaction_response_json` 保存用户回答；回答必须引用同会话同章节的来源助手消息，服务端校验问题和选项归属并生成可读正文。任何交互都只产生讨论候选，不自动确认作品资产。用户消息可携带 `referencedMessageId`，仅允许引用当前会话、章节与作品范围内可见的 user 或 assistant 消息；读取结果返回服务端截断的角色与预览，模型上下文仍使用原消息全文。失效、跨范围或系统消息引用统一返回 `MESSAGE_REFERENCE_INVALID`，不返回目标内容。消息也可携带仅含 `briefId + decisionKey` 的 `discussionFocus`，服务端验证其为当前最新草稿中的未确认待决，并从数据库解析待决、结构化共识和同会话来源消息后写入 Story Context Snapshot。任务遇到未预期运行时异常时会记录 taskId、chapterId、异常类型和堆栈，但不记录密钥、Token 或完整 Prompt。
- 章节结构化共识能力：`chapter_briefs.brief_content` 兼容保存 `ChapterConsensusContentV1` JSON 与历史自由文本；新草稿始终追加，只有创建时间晚于 latest confirmed 的 draft 才是可操作当前态。模型异步收束任务只能创建 draft，用户确认使用 Brief `version` 条件更新；重新整理以当前草稿或已确认版本为基础，已由用户处理为 `confirmed`、`rejected` 或 `discussing` 的决定会原样保留，模型不能将其降级为候选。必要待决未解决时不能确认；候选处理通过 `POST /api/chapters/{chapterId}/briefs/{briefId}/decisions/{decisionKey}/resolve` 追加新草稿，支持 adopt、reject、discuss 和版本冲突保护。模型来源同时保存消息 ID 与精确原文摘录，来源接口按消息返回 quotes；历史文本明确返回 `legacy_text`，不伪造结构化共识。
- 章节大纲与生成能力：`chapter_outlines` 是正式章节大纲事实源。`POST /api/chapters/{chapterId}/outline/candidates` 通过 `candidateType=initial/adjustment` 同时支持从 latest confirmed Brief 生成首版章纲候选，以及基于正式大纲快照生成调整候选；V2 任务快照保存类型、引用和幂等键，旧调整任务输入继续兼容。首版候选不绑定基础大纲，同章创建事务串行化并以章节级幂等键复用请求；只有确认时且正式大纲仍不存在才创建 revision 0 的正式大纲。调整候选确认继续以 `id + revision + version + deleted` 条件更新。候选生成、编辑、失败、取消或放弃均不修改正式大纲，`PUT .../candidates/{candidateId}` 只允许以候选 `version` 编辑 ready 内容并重算差异与共识影响。兼容路径 `/outline/refresh` 仍只映射为 adjustment 候选创建。`chapter_generations` 固定保存已确认 Brief ID、版本、大纲 ID/revision、生成参数与依据快照。
- 章节正文与发布能力：未建立 Story Release 的旧章节继续支持 `chapters.version` 条件保存；一旦章节拥有 `current_prose_revision_id`，旧保存与生成采纳 SQL 不再允许原地覆盖发布正文。章节列表与详情均返回可空 `currentProseRevisionId`，客户端以此持久化发布指针判断正文只读状态，不从 `workflowStatus` 猜测 Story Release 事实。新编辑通过 `/api/works/{workId}/story-revisions` 创建不可变 revision，绑定正文哈希一致的 #105 整章评价，加入固定基线的作品修订工作区，并在对应 revision 的 `/impact-reports` 子资源完成影响报告；缺失、失败、运行中、低置信、`unknown` 或来源已 stale 的报告会阻塞 prepare。存在事实变化时，还必须等待绑定该 prose revision 的 ready 知识批次，且所有候选均由用户明确处理为 confirmed/ignored。只有用户显式确认后才原子发布或回退。
- 长篇知识层能力：按作品筛选候选设定和正式设定；正文 generation 被采纳且事务提交后，`story_knowledge_extraction_v1` Agent Run 会基于冻结的正文 revision 和指纹幂等提取章节摘要、关键事件、设定和伏笔候选。结构化输出必须携带正文证据范围并通过作品归属与引用校验；完全相同内容标记 `duplicate`，命中既有权威资产但内容不同标记 `conflict`。自动流程只写入 `story_knowledge_candidates`，用户以候选版本显式确认后才创建、合并或替换正式知识；来源变化时批次进入 `stale`。既有设定候选确认仍先锁定候选父行，再在同一事务内创建或合并正式设定并更新状态；候选、正式设定和伏笔列表支持稳定分页。
- 用户配置能力：当前用户固定为 `local-user`，只开放 `model.active`、`writing.preferences`、`appearance.preferences`、`sync.preferences` 四类配置，并使用 `baseVersion/version` 做乐观锁控制。缺失配置读取返回版本 `0` 和空对象，客户端可基于版本 `0` 创建，创建成功后的持久化版本为 `1`；并发创建触发唯一键竞争时返回 `CONFIG_VERSION_CONFLICT`。
- 配置安全边界：通用 `configValue` 保存会递归拒绝 `apiKey`、`accessKey`、`privateKey`、`token/tokens`、`secret`、`clientSecrets`、`password`、`credential` 等明文敏感键。仅 `model.active` 的请求顶层允许受控提交 `apiKey` 或 `clearApiKey`：Key 缺省或空白时保留、非空时替换、删除标记为 true 时清除，二者同时出现返回 400。Key 使用 AES-256-GCM、随机 nonce 和用户/供应商/凭据类型 AAD 写入 `llm_credentials`，不进入 `user_configs.config_value`；读取只返回 `apiKeyConfigured` 和表内安全末尾摘要。
- 模型状态能力：`GET /api/system/model-status` 只读取当前配置和最近测试结果，不发起网络请求；`POST /api/system/model-status/test` 使用已保存配置发送最大 64 token 的最小 DeepSeek 请求。成功或安全错误按原配置版本条件写回 `lastTestStatus`、`lastError`、`lastTestedAt` 并递增配置版本，测试期间配置变化返回 `CONFIG_VERSION_CONFLICT`；只有 Key 已配置且最近测试成功时 `available=true`。
- AI 任务能力：提供 `ai_tasks` 查询、幂等取消和失败讨论回复重试，只接受 `queued`、`running`、`succeeded`、`failed`、`canceled` 五种状态；`POST /api/ai-tasks/{taskId}/retry` 只重新投递失败的 `conversation_reply`，以状态和版本条件将原任务恢复到 `queued`，保留 task ID、创建时间、用户消息、讨论焦点和上下文快照，不新建用户消息。讨论回复、章节共识和大纲候选任务领取、完成、失败与取消均使用状态和版本条件更新。`chapter_consensus` 与 `outline_adjustment_candidate` 的 `task_input_json` 仅保存可恢复的资源 ID、基础 revision 和用户要求；任务详情通过 `result_brief_id` 或 `result_outline_candidate_id` 恢复结果。Provider 调用不在数据库事务内，结果和任务成功状态在短事务中原子绑定。

## 接口与数据流

- 当前已实现接口覆盖：作品章节、章节共创会话、带可选 `referencedMessageId`、待决对焦和 `replyControl` 的会话消息、回复深度分层偏好、章节 Brief 状态/追加/确认/来源查询/异步收束、章节大纲读取/保存/首版与调整候选创建/查询/编辑/放弃/确认、章节生成创建/详情/最近预览/采纳/拒绝/重新生成、隔离的章节生成策略实验、章节正文读取/保存、正文 revision/差异/评价绑定/放弃、revision 子资源下的正文影响报告创建/latest/detail/retry、作品修订工作区准备/发布/放弃及结构化影响摘要、Story Release 查询/比较/回退，以及设定候选查询/确认/忽略、正式设定查询、伏笔查询/创建、章节摘要、关键事件、用户配置、模型状态与连接测试、AI 任务查询/取消/失败讨论回复重试、Agent Run 当前状态和 LLM 调用明细/聚合查询。
- LLM 调用观测接口为 `GET /api/llm-calls` 与 `GET /api/llm-calls/summary`。业务调用点只提供白名单 `LlmCallContext`，`ObservedLlmProvider` 装饰器统一维护同步、流式和连接测试调用的开始、终态、token、耗时与安全错误；逻辑调用和物理重试分别用 `logical_call_id`、`attempt_no` 表示。查询按固定本地用户隔离，支持最近 30 天默认窗口、稳定分页及日期/用户/作品/模型/工作流白名单聚合，详细契约见 `docs/LLM调用观测接口.md`。
- 大纲候选接口为：`POST /api/chapters/{chapterId}/outline/candidates`、`GET /api/chapters/{chapterId}/outline/candidates/latest`、`GET/PUT /api/chapters/{chapterId}/outline/candidates/{candidateId}`、`POST .../{candidateId}/abandon`、`POST .../{candidateId}/confirm`。候选状态为 `queued/running/ready/failed/canceled/abandoned/confirmed`；详情返回 `candidateType`、`idempotencyKey`、候选 `version`、绑定 Brief、可空基础大纲快照、结构化候选内容、确定性差异、三维共识影响和确认后的正式大纲引用。
- 章节生成创建接口同步返回 `draft` 资源标识，本地生成完成后生成记录进入 `preview`、关联 `ai_tasks` 进入 `succeeded`；生成器通过 `ChapterContentGenerator` 接口隔离，当前实现根据章节标题、brief、大纲快照和生成参数确定性构造中文预览，不调用真实 LLM。
- 创建和重新生成响应中的 `gmtCreate` 以生成记录持久化后的重新查询结果为准，不依赖数据库默认时间自动回填到插入实体；最近预览查询在数据库侧按创建时间和 ID 倒序并 `LIMIT 1`，且只读取预览摘要字段。
- 大纲和生成只读取显式指定或数据库侧按状态限一查出的 latest confirmed Brief；没有 confirmed Brief 时返回 `CHAPTER_CONFIRMED_BRIEF_REQUIRED`。生成依据快照保存 `confirmedBriefId`、`confirmedBriefVersion` 和生成时的 Brief 内容，重新生成继续使用原快照，不重新猜测 latest。
- 生成稿仅在 `preview` 状态可首次采纳或拒绝；采纳支持 `replace` 和 `append`，已采纳记录重复请求直接返回当前结果，不会二次写入正文。重新生成会创建新的 generation/task，并保留原依据、合并本次反馈。
- Web 层将 `page=abc`、整数溢出等请求参数类型转换失败统一映射为 `BAD_REQUEST` 和 HTTP 400；候选状态竞争与 AI 任务取消竞争分别返回 `SETTING_CANDIDATE_CONFLICT`、`AI_TASK_STATE_CONFLICT` 和 HTTP 409。
- 当前主流程数据流为：作品/章节创建 -> 章节共创消息沉淀 -> Brief 与大纲收束 -> 章节生成候选 -> 独立评价/有界修订 -> 用户选择正文 revision -> 作品修订工作区 -> 用户确认 Story Release 原子切换 -> 后续知识候选。
- 已发布正文以当前 `story_releases` 的完整章节 revision 映射为版本事实源；`works.current_story_release_id`、`chapters.current_prose_revision_id` 和 `chapters.content` 在同一事务中切换，后者是兼容既有读取链的当前正文投影，不允许脱离 release 原地覆盖。回退到缺少后来新增章节的旧快照时，该章节公开指针与正文投影按版本条件清空。尚未建立首个 release 的旧数据继续按原正文接口兼容。
- 当前接口文档不覆盖：正式前端页面、角色状态快照、叙事线程、时间线、知识巡检、外部 APM、供应商账单对账和独立 `suggestions` 接口。正文知识提取契约见 `docs/正文知识提取接口.md`；真实 Provider、数据库与 UI 闭环由 Issue #81 统一验收。

## 数据库与持久化要点

- 当前数据库迁移由 `moqi-start/src/main/resources/db/migration` 下的 Flyway SQL 管理，当前有效版本为 V1-V20、V22-V42；V21 未被占用。
- 当前数据库结构说明统一看 `docs/2026-06-09-数据库设计.md`；迁移历史和设计调整记录统一看 `docs/数据库设计变更记录.md`。
- P0 主流程以 `works`、`chapters`、`chapter_conversations`、`chapter_conversation_messages`、`chapter_briefs`、`chapter_generations` 为已落库基础。
- `chapter_prose_revisions` 冻结正文、SHA-256 哈希、父 revision、来源 generation/#106 修订/来源快照和 #105 评价；内容字段没有更新入口。评价报告除作品、章节和正文哈希一致外，还必须精确绑定 revision 的来源 generation，防止相同正文的不同生成调用串用 Brief、来源指纹或模型调用审计链；没有来源 generation 的手工 revision 保持不可发布。`bounded_revision` generation 不能省略 #106 来源任务，且只能绑定该任务的 `resultReportId`；任务必须已由同一 result generation 的可采纳报告恢复为 `candidate_ready`，失败、`needs_human` 或尚未完成重评均不能进入发布链。`story_releases` 与 `story_release_chapters` 冻结作品级发布基线，`work_revision_workspaces` 与其章节项保存待发布 revision、基线 release、章节版本和阻塞项。作品和章节当前指针只通过发布或回退事务切换。
- 自 issue #18 起，新增数据库表默认使用 `id`、`gmt_create`、`gmt_modified` 作为基础字段；历史 V1-V3 中的 `created_at/updated_at` 通过增量迁移改名，不重写旧迁移。
- `chapter_outlines` 是正式章节大纲事实源，一章一条，使用 `outline_content JSON` 保存现有章纲结构，并用 `revision` 支撑业务修订冲突控制；`version` 与继承 `BaseEntity` 的通用 MyBatis-Plus 映射保持一致，`confirmed_brief_id` 固化本次章纲承接的已确认共识。`chapter_outline_candidates` 保存 `initial/adjustment` 类型、章节级幂等键、候选任务、会话/Brief、可空基础快照、候选内容、差异、共识影响和确认结果，候选不作为正式章纲事实源。
- `chapter_briefs` 是章节共创收束历史；`draft` 允许继续讨论和修改，只有用户通过确认接口产生的 `confirmed` 才能进入大纲和正文生成。结构化 V1 与历史自由文本继续共用 `brief_content LONGTEXT`。
- `user_configs` 是用户级通用配置表，首版用于承载模型配置、写作偏好、外观和同步配置；暂不单独设计 `model_providers`。
- `user_configs` 的首次创建从缺失态版本 `0` 推进到版本 `1`，并依靠用户、配置键和软删除标记的唯一约束阻止并发创建覆盖；后续更新使用当前行 `version` 作为条件执行原子更新；配置值使用结构化 JSON 解析和序列化。
- `ai_tasks` 承载 AI 回复、共识收束、正文生成和大纲调整候选等异步任务状态，供轮询和取消接口使用；`context_snapshot_id` 追溯实际模型上下文，`task_input_json` 保存可恢复 ID 引用，`result_brief_id` 与 `result_outline_candidate_id` 分别保存共识和候选任务结果。
- `llm_model_calls` 记录每次 Provider 尝试并关联 AI Task、Agent Run/Step、用户、作品和章节；`llm_model_prices` 保存带生效区间的 Provider/模型单价版本。成本按调用时间命中价格版本，当前因 usage 未区分缓存命中 token，输入成本按 cache miss 单价保守估算并明确标记 `estimated`；缺少 usage 或单价时标记 `unpriced`。两张表不保存 API Key、完整 Prompt、正文或隐藏推理。
- 场景规划使用 `chapter_plan_versions` 和 `scene_plan_versions`；历史 `work_narrative_plan_versions` 及旧候选中的作品规划引用只保留用于兼容和审计，不再提供作品规划 HTTP 写入口，也不再作为新场景候选的来源或生成门槛。创建场景候选时会锁定章节，并固化 `SCENE_PLANNING` Story Context Snapshot：只包含已确认 Brief、正式章纲和被选入的 active 设定、伏笔与已确认章节摘要，不包含完整聊天记录、草稿、已否定候选或历史作品规划。快照 ID、来源指纹与来源链绑定到 AI Task、Agent Run 和候选；同一幂等键且来源一致会复用原候选，来源变化返回 `AGENT_RUN_IDEMPOTENCY_CONFLICT`。模型从固化快照生成内容 schema v2 `scenes`，在既有目标、冲突和结果之外显式记录读者认知、因果前置、地点承接、状态变化、连续性、叙事权重、自由发挥和禁止发明；所有自动场景必须为 `planned`，引用只能指向快照中已有的设定和伏笔。历史 v1 缺失语义只投影为空值和 `unspecified`，不会被推断或静默回写。章纲在执行或写入前变化时返回 `SCENE_PLAN_SOURCE_STALE`，候选进入 `stale` 且不写入场景；已发布版本始终不被自动覆盖。场景修订桥接接口可把同章当前已发布规划确定性克隆为不关联 AI 任务的 `ready` 草稿，并在一致性报告与版本归属均有效时，将已发布版和草稿的场景差异作为来源证据交给现有章纲调整候选流程；两步都按幂等键复用，且不会自动确认章纲或发布场景规划。章纲候选确认后，修订草稿进入 `needs_review`；最新候选查询继续返回该状态，并携带已发布来源规划 ID 与版本，供前端刷新后恢复复核门禁。
- `setting_candidates` 是 `setting_entries.source_candidate_id` 的外键父表；候选确认事务必须先锁定候选行，再写入或更新正式设定，最后按锁定快照的 `pending/version/deleted` 条件更新候选状态。
- `story_knowledge_extraction_batches` 固化已采纳 generation、正文 revision、来源指纹、提取器版本、AI Task 和 Agent Run；同一 generation 与提取器版本唯一。`story_knowledge_candidates` 保存结构化 payload、精确正文证据、去重/冲突目标和用户确认后的权威目标。两表不保存完整 Prompt 或隐藏推理，候选确认前必须重新验证来源未过期。
- `prose_revision_impact_reports` 固定 baseline/target revision、workspace/release 基线、正文输入指纹、V24 来源图指纹、分析器版本、Agent Run、模型调用、状态、范围和阻塞结论；`prose_revision_fact_changes` 保存经过正文精确范围复核的事实变化与认知属性，`prose_revision_impacted_assets` 保存通过 V24 来源快照解析出的真实下游资产。V41 建立四张正文影响与 release 知识来源表，V42 以增量列绑定来源图指纹和精确受影响章节；V42 前生成的历史报告因缺少来源图身份会安全视为 stale，需重新生成。`story_release_knowledge_sources` 将用户已确认知识绑定到 prose revision 与 Story Release；同 release 同知识目标按最小来源 candidate ID 确定性去重，完整候选证据继续保留在原批次。新 release 的映射准备、旧映射失活和新映射激活只在 Story Release 发布/回退事务内完成，失败时整笔回滚，旧 release 在提交前持续有效。
- 自 issue #18 的后续迁移起，P0 主流程相关表统一补充中文表注释和字段注释，便于通过数据库工具直接理解表语义。
- 当前 P0 数据库不保留 `biz_id` 业务唯一 ID 列，统一使用自增 `id` 作为主键和关联键。
- issue #22 起，数据库补充长篇小说知识层最小结构：`setting_candidates` 保存待确认设定，`setting_entries` 保存正式作品级设定，`foreshadowing_items` 保存伏笔与线索，`chapter_summaries` 保存章节摘要，`chapter_key_events` 保存章节关键事件。
- `chapters.chapter_type` 用于区分 `dedication`、`prologue`、`chapter`、`epilogue`、`other`，导入既有小说时应保留献词、序幕、尾声等非标准正文块。

## Agent Runtime 技术验证边界

- Issue #43 已将 Spring AI Alibaba Graph Core `1.1.2.2` 接入 `moqi-service` 的内部适配层；Graph 类型仅位于 `agent.infrastructure`，业务 Service、Controller、SSE 和持久化契约不依赖框架类型。Graph Core 的无关数据库、RAG、Redisson、Mongo、MCP 与 Commons Exec 传递依赖被排除；其静态序列化器强制链接的 ZhiPuAI 类保留为二进制依赖，但未启用任何 ZhiPuAI Provider。
- `AgentRuntime` 提供启动、按用户读取、恢复、恢复令牌重签、单步重试和取消端口；`agent_runs`、`agent_run_steps`、`agent_checkpoints`、`agent_interruptions` 分别保存多步骤状态、尝试记录、版本化 JSON checkpoint 和人工恢复令牌哈希。幂等键绑定完整启动请求，人工恢复从 checkpoint 的下一步骤继续，并把校验后的确认内容作为后续步骤输入。`GET /api/agent-runs/{runId}` 仅用于 SSE 断线后读取持久化事实，当前按固定用户 `local-user` 校验归属，不暴露 checkpoint 内容或恢复 token；通用工作流启动、恢复和取消仍由后续具体小说工作流通过内部端口接入。恢复语义见 `docs/Agent Runtime 恢复语义.md`。
- 技术决策为部分采用：后续可在内部适配层使用 Graph Core 的编排能力，但业务 Service、SSE 和领域模型不得依赖框架类型。
- Spring AI Alibaba `1.1.2.2` 内置 `MysqlSaver` 的 checkpoint 缺少稳定单调顺序，同秒多 checkpoint 的重启恢复存在非确定性；生产实现不得直接采用该 Saver 或其 Java 对象序列化载荷。
- 后续生产 checkpoint 必须使用 Moqi 自有、可版本化的 JSON 契约和确定性 sequence，并以数据库条件更新保证确认、取消和 resume 幂等。详细证据、退出条件和备选状态机见 `docs/adr/ADR-0001-Spring-AI-Alibaba-Graph-运行时技术验证.md`。

# 项目结构与功能介绍

## 场景小说生成恢复边界

作品叙事规划的历史表和已有来源引用仅用于兼容和审计，作品规划 HTTP 路由不再对外暴露；新场景候选允许作品规划来源为空。

章节正文生成以 `chapter_generations`、`chapter_generation_scenes`、`chapter_capacity_assessments`、`agent_runs` 与 `agent_run_steps` 为事实源。常规 `all` 批次不创建待执行场景行，而是一次生成 `whole_chapter_once` 并直接持久化 generation；局部和历史批次继续使用场景行。Brief/实体卡预览保持只读，容量评估保持候选和门禁语义。正式整章 Prompt 只使用冻结 Brief、容量软区间、事件叙事权重、不可压缩因果节点和可选参考基稿，不按场景数量平均分配字数，也不在恢复时重新评估或读取当前来源。SSE 增量只用于即时显示；刷新、重连或进程重启后通过章节最新活动批次和 Agent Step 的持久化 `currentAttempt`、`retryable` 恢复，不由客户端猜测运行状态。

## 章节共识自动收束边界

章节共识作用域候选使用 `chapter_consensus_scope_candidates` 保存待人工分流结果；候选确认仅改变候选状态，当前不自动写入角色、设定、世界观等权威资产，Story Context 继续只读取既有已确认资产。

Issue #57 在讨论助手回复的持久化事务提交后，按会话和助手消息创建幂等的 `chapter_consensus_maturity_v1` Agent Run。工作流依次完成确定性预检、结构化成熟度判断和既有 `chapter_consensus` Draft 任务提交；失败、取消或超时不会影响原回复。成熟度结果只保存安全摘要，自动流程不会确认或覆盖 Brief。阈值与超时由 `moqi.chapter.consensus-maturity` 配置。

## 场景规划真实工作流边界

场景规划候选通过受观测的 Provider 生成结构化 `scenes`，当前生成输入明确要求基于正式章纲创建候选。工作流向模型提供正式章纲的稳定节拍键，并在落库前校验每个场景均有关联、引用键合法、全部节拍已覆盖且首次出现顺序未倒置，避免生成无法通过一致性检查的候选。Provider、JSON、结构校验和持久化失败稳定映射为 `SCENE_PLAN_PROVIDER_FAILED`、`SCENE_PLAN_JSON_INVALID`、`SCENE_PLAN_VALIDATION_FAILED`、`SCENE_PLAN_PERSISTENCE_FAILED`；候选状态推进和场景叶子写入处于同一事务，写入失败不会遗留 `ready` 但缺少场景的候选。

## 正文候选一致性评价

`chapter_generation_evaluation_reports` 固化完整正文哈希、`basisSnapshotJson`、#47 资产来源快照及其解析出的 Story Context Snapshot，`context_snapshot_id` 只保存资产快照的 `sourceContextSnapshotId`，不得把 `chapter_generations.source_snapshot_id` 直接当作 Story Context ID。报告同时保存 Brief/完整来源指纹、规则与 Evaluator 版本、独立 `llm_model_calls` 引用、安全失败摘要和可定位 Finding。`chapter_generation_evaluation_v1` 只执行确定性检查、`whole-chapter-evaluator-v3` 结构化语义评价和 `pass/warning/needs_revision/needs_human` 聚合；模型输出先按字段路径和类型整批校验，只对证据文本包装、整章场景误填、来源快照无法验证的 Story Fact 引用及非阻塞项的自动修订误标做单向安全收敛，规范化路径留在 Agent Step 输出。它不生成 #106 修订稿，也不写入 `chapters.content` 或权威资料。相同正文与版本键幂等复用；正文、Brief/basis、资产来源或 context/source 任一变化都使旧报告过期，失败、超时、取消和旧报告都不能满足采纳门禁。

评价报告 View 只在报告为 `failed` 且关联 Run 的工作流、作品、章节和 AI Task 归属全部可靠时，从最新 `semantic_evaluate` Step 返回 `currentAttempt`；只有 Run/Step 同为 failed 且 Runtime 持久化 `retryable=1` 时才返回 `retryable=true`。queued、running、ready、canceled 或归属缺失均返回 `null/false`，且不使用评价报告的 `revisionAttempt` 回退。重试继续提交 `expectedAttempt`，报告版本/状态 CAS 与 Agent Runtime Step CAS 共同拒绝旧 attempt 和重复点击；冲突不会创建新 Run、Step 或模型调用。Runtime 接受重试时按当前工作流时限重新计算 `timeout_at`，避免历史失败 Run 沿用已过期截止时间而在新 attempt 领取前被误判超时。

`bounded_chapter_revisions` 将整章评价中的高置信、可自动修订且证据范围明确的多个兼容 Finding 固化为任务书。`POST /api/chapters/{chapterId}/generations/{generationId}/bounded-revisions` 在 P0 对每个来源候选最多启动一轮；来源冲突、低置信、需要修改规划或权威设定、Finding 预算耗尽均直接停止为 `needs_human`。工作流只生成完整的新 `chapter_generations` preview，保留 `base_generation_id`、原文、任务书、模型调用和来源快照，不覆盖原稿、已采纳正文或知识资产；新候选以新正文哈希自动启动独立整章评价。查询接口从关联报告恢复 `candidate_ready/needs_human`；统一 `requireAdoptable` 门禁还会核对 result generation 的唯一未删除任务、精确 `resultReportId`、正文哈希、作品章节归属和可采纳结论，legacy generation accept 与 Story Release 共用该约束，alternate latest report、失败或人工处理状态均不能放行。最终选版和采纳始终由用户显式执行。

## 已采纳正文知识提取

正文 generation 首次或幂等重复采纳后发布事务后事件，失败隔离的监听器创建 `story_knowledge_extraction_v1` Agent Run。工作流固定执行来源预检、结构化 Provider 提取、Schema/证据/归属校验和候选持久化；重试和重启复用批次中冻结的正文，不重新读取聊天记录或未确认候选。自动结果仅为 `pending/conflict/duplicate` 候选，确认接口再次检查正文来源和候选版本，只有用户显式决定后才写入摘要、关键事件、正式设定或伏笔。

## 场景规划一致性检查

场景规划中的 `outlineBeatKeys` 显式关联 V2 章纲节拍。`scene_plan_consistency_reports` 保存计划快照、来源指纹和安全 Finding 摘要；报告通过 Agent Runtime 依次执行预检、规则检查、语义评估和收束，报告本身不修改场景或权威故事资产。发布必须绑定当前计划版本的 `ready` 报告：`conflict` 阻断发布，`unknown` 必须由用户显式确认，`extension` 和 `compatible` 可发布。正文生成只允许消费带有效报告的当前已发布规划。需要进一步讨论的 `extension`、`conflict`、`unknown` Finding 会创建来源可追溯的 Brief 草稿，绝不伪造历史消息或自动确认共识。

## 章节选区讨论与局部改写候选

`chapter_selection_assistance` 保存正文版本与哈希、选区偏移和原文、有限相邻段落、只读 Chapter Generation Brief 指纹、幂等键、父候选、Agent Run 及安全的模型结果。`discuss` 只产生建议；`rewrite`、`polish`、`expand`、`compress` 只产生待人工采纳候选，继续修改通过父候选创建新记录，不覆盖历史结果。刷新或服务重启后，客户端通过 `GET /api/selection-assistance/{requestId}` 重取持久化状态，并可对失败步骤执行重试或取消。

采纳是显式短事务：后端锁定章节并同时校验 `workflow_status=co_creation`、正文版本、全文 SHA-256、选区偏移和选区原文，再通过 `chapters.version` 乐观锁替换局部正文。已发布章节只允许讨论，不能直接创建或采纳改写候选。模型输出中的事实变化不确定性默认标记为 `review_required`，接口仅提示用户可提交规划变更，不会自动确认正文、发布章节或写入规划与知识资产；持久化记录也不保存完整系统 Prompt、隐藏推理或无关整章正文。
