# 墨契后端项目结构与功能介绍

## 文档目的

这份文档用于帮助新会话、新协作者或未来回看代码的人快速理解后端项目当前的结构、功能和运行约束。
它不是一次性说明，而是随着模块、接口、数据结构和运行约束演进持续补充的后端项目介绍文档。

## 场景小说生成工作流

- `chapter.service.SceneGenerationService` 负责创建、重生成、查询、取消和单场景重试；请求只能引用本章节已发布的 ScenePlan，`all`、`continue_from` 和 `rewrite_selected` 三种选择模式均保存为独立批次。
- `chapter.workflow.SceneNovelGenerationWorkflowDefinition` 通过 Agent Runtime 逐场景调用 Provider V2，并将上下文快照、模板版本、模型调用审计与候选状态写入短事务；远程模型调用不位于数据库事务中。
- `chapter_generation_scenes` 保存候选正文，`llm_model_calls` 保存脱敏的模型审计数据。候选完成不自动覆盖章节正式正文，采纳仍沿用既有正文版本控制。
- 章节讨论回复由 `chapter.policy` 在消息创建时解析为 `clarify/compare/converge/plan/draft` 与 `brief/balanced/deep`，并以 `ConversationReplyTaskInputV1` 写入 `ai_tasks.task_input_json`；失败重试只消费原策略快照。深度优先级为单次控制、会话、章节、作品、用户、系统，偏好通过 `/api/reply-policy/preferences` 读写。Story Context V2 将已确认、候选、待决、已否定和证据分层，旧快照缺失状态时降级为 evidence；完整规则见 `docs/章节讨论自适应回复策略.md`。
- `ChapterSseRegistry` 转发场景生成资源事件；客户端收到事件后重新读取批次或场景，不能从 SSE 获得正文、prompt 或凭据。
- 详细请求结构、状态和错误语义见 `docs/场景小说生成接口.md`；恢复和重试边界见 `docs/Agent Runtime 恢复语义.md`。

## 当前项目定位

- Moqi 后端当前承担写作主流程的数据与服务基础：作品、章节、章节共创、章节大纲/简报、章节生成、章节正文保存，以及长篇小说第一版必通知识层。
- 当前接口文档生成应以 P0 写作主流程和已落库知识层为准，不为尚未落库的增强能力生成正式接口。

## 当前模块与分层概览

- `moqi-start` 是 Spring Boot 启动模块，负责装配配置、扫描组件并承载 Flyway 迁移资源。
- `moqi-web` 是 Web 接入层，包含健康检查、作品章节、章节共创、知识层、用户配置、模型状态、AI 任务和 Agent Run 只读查询 Controller，以及全局异常处理。
- `moqi-service` 是业务服务层，承载应用服务和领域流程编排。
- `moqi-service` 通过 Provider V2 的有序消息、通用选项、响应元数据、统一流事件、能力声明和 `LlmStreamCall` 隔离厂商协议；DeepSeek 是首个实现，Factory 与上层业务只接收供应商无关运行时配置。Provider 每次按数据库配置和最小作用域解密的凭据动态创建，不缓存包含 Key 的客户端。
- `moqi-dal` 是数据访问层，包含 MyBatis-Plus 实体与 Mapper；当前已有作品、章节、章节共创、章节生成、知识层和大模型凭据相关实体。
- `moqi-dal` 的持久化实体统一使用 Lombok `@Data` 生成机械方法，不重复声明 `@Getter`、`@Setter`。Lombok 仅作为编译期依赖，不参与运行时逻辑。
- `moqi-common` 是公共基础模块，包含统一响应、错误码和业务异常等跨模块基础类型。
- 所有生产与测试 Java 顶层类型均在 import 区域之后、类型级注解和声明之前维护作者、创建日期和职责说明；具体模板与填写规则以仓库根目录 `AGENTS.md` 为准。

## 构建与规范检查

- Codex 的项目级工作方式由本仓库 `AGENTS.md` 约束：标准业务开发可使用 `DgnCoding`，已有计划进入执行时可使用 `executing-plans`，重型自动循环只在用户明确要求时启用。仓库不使用项目级 `.codex/config.toml` 选择性禁用用户 Skill，避免配置语法有效但运行时未参与 Skill 过滤。
- 当前运行基线为 Java 17、Spring Boot 3.5.8、Spring AI Alibaba 1.1.2.2 和 Spring AI 1.1.2，并使用 `spring-ai-starter-model-deepseek` 对接 DeepSeek Chat 模型。
- 后端使用多模块 Maven 构建，提交前执行 `mvn clean verify` 和 `git diff --check`。
- 根 `pom.xml` 在 Maven `verify` 阶段为各 Java 模块执行 Alibaba P3C PMD 检查，检查结果写入各模块的 `target/pmd.xml`。
- P3C 当前采用报告模式，`failOnViolation=false`；规范违规会出现在 Maven 日志和报告中，但不会因此阻断编译、测试、验证或打包。
- Maven `BUILD SUCCESS` 仅表示构建和测试成功，不表示 P3C 无违规；交付时必须分别报告 Maven 结果、P3C 结果和遗留规范问题。

## 主要功能与服务说明

- 作品与章节能力：保存作品基础信息、章节标题、章节顺序、章节类型、正文和工作流状态。
- 章节共创能力：用户通过普通 POST 提交消息；当请求创建 `conversation_reply` 任务时，事务提交后由有界线程池异步调用已验证可用的 DeepSeek Provider，逐段产生回复事件，最终持久化 assistant 消息并将 `ai_tasks.result_message_id` 指向该消息。消息可携带仅含 `briefId + decisionKey` 的 `discussionFocus`，服务端验证其为当前最新草稿中的未确认待决，并从数据库解析待决、结构化共识和同会话来源消息后写入 Story Context Snapshot。任务遇到未预期运行时异常时会记录 taskId、chapterId、异常类型和堆栈，但不记录密钥、Token 或完整 Prompt。
- 章节结构化共识能力：`chapter_briefs.brief_content` 兼容保存 `ChapterConsensusContentV1` JSON 与历史自由文本；新草稿始终追加，只有创建时间晚于 latest confirmed 的 draft 才是可操作当前态。模型异步收束任务只能创建 draft，用户确认使用 Brief `version` 条件更新；重新整理以当前草稿或已确认版本为基础，已由用户处理为 `confirmed`、`rejected` 或 `discussing` 的决定会原样保留，模型不能将其降级为候选。必要待决未解决时不能确认；候选处理通过 `POST /api/chapters/{chapterId}/briefs/{briefId}/decisions/{decisionKey}/resolve` 追加新草稿，支持 adopt、reject、discuss 和版本冲突保护。模型来源同时保存消息 ID 与精确原文摘录，来源接口按消息返回 quotes；历史文本明确返回 `legacy_text`，不伪造结构化共识。
- 章节大纲与生成能力：`chapter_outlines` 是正式章节大纲事实源，手工保存和候选确认统一以 `id + revision + version + deleted` 条件更新，成功时 `revision/version` 各递增一次。`POST /api/chapters/{chapterId}/outline/candidates` 基于指定已确认 Brief、正式大纲快照和调整要求创建异步候选；候选生成、失败、取消或放弃均不修改正式大纲，只有 `confirm` 才会落版。兼容路径 `/outline/refresh` 仅映射为候选创建。`chapter_generations` 固定保存已确认 Brief ID、版本、大纲 ID/revision、生成参数与依据快照，支持预览查询、采纳、拒绝和基于原依据重新生成。
- 章节正文能力：提供章节正文读取和条件保存接口；手工保存与生成稿采纳都使用 `chapters.version` 条件更新，冲突时返回服务端正文、版本与保存时间。
- 长篇知识层能力：按作品筛选候选设定和正式设定，确认候选时先通过 `SELECT ... FOR UPDATE` 锁定候选父行，再在同一事务内创建或合并正式设定并更新候选状态，避免外键子表插入后的父行锁升级竞争；候选确认和忽略使用 `pending` 状态、版本及软删除条件做原子更新，合并正式设定同样检查版本和软删除状态；候选、正式设定和伏笔列表支持可选 `page/pageSize`，默认第 `1` 页、每页 `50` 条、上限 `100` 条，并按更新时间和 ID 倒序稳定分页；支持幂等忽略、伏笔创建、章节摘要和关键事件读取。
- 用户配置能力：当前用户固定为 `local-user`，只开放 `model.active`、`writing.preferences`、`appearance.preferences`、`sync.preferences` 四类配置，并使用 `baseVersion/version` 做乐观锁控制。缺失配置读取返回版本 `0` 和空对象，客户端可基于版本 `0` 创建，创建成功后的持久化版本为 `1`；并发创建触发唯一键竞争时返回 `CONFIG_VERSION_CONFLICT`。
- 配置安全边界：通用 `configValue` 保存会递归拒绝 `apiKey`、`accessKey`、`privateKey`、`token/tokens`、`secret`、`clientSecrets`、`password`、`credential` 等明文敏感键。仅 `model.active` 的请求顶层允许受控提交 `apiKey` 或 `clearApiKey`：Key 缺省或空白时保留、非空时替换、删除标记为 true 时清除，二者同时出现返回 400。Key 使用 AES-256-GCM、随机 nonce 和用户/供应商/凭据类型 AAD 写入 `llm_credentials`，不进入 `user_configs.config_value`；读取只返回 `apiKeyConfigured` 和表内安全末尾摘要。
- 模型状态能力：`GET /api/system/model-status` 只读取当前配置和最近测试结果，不发起网络请求；`POST /api/system/model-status/test` 使用已保存配置发送最大 64 token 的最小 DeepSeek 请求。成功或安全错误按原配置版本条件写回 `lastTestStatus`、`lastError`、`lastTestedAt` 并递增配置版本，测试期间配置变化返回 `CONFIG_VERSION_CONFLICT`；只有 Key 已配置且最近测试成功时 `available=true`。
- AI 任务能力：提供 `ai_tasks` 查询、幂等取消和失败讨论回复重试，只接受 `queued`、`running`、`succeeded`、`failed`、`canceled` 五种状态；`POST /api/ai-tasks/{taskId}/retry` 只重新投递失败的 `conversation_reply`，以状态和版本条件将原任务恢复到 `queued`，保留 task ID、创建时间、用户消息、讨论焦点和上下文快照，不新建用户消息。讨论回复、章节共识和大纲候选任务领取、完成、失败与取消均使用状态和版本条件更新。`chapter_consensus` 与 `outline_adjustment_candidate` 的 `task_input_json` 仅保存可恢复的资源 ID、基础 revision 和用户要求；任务详情通过 `result_brief_id` 或 `result_outline_candidate_id` 恢复结果。Provider 调用不在数据库事务内，结果和任务成功状态在短事务中原子绑定。

## 接口与数据流

- 当前已实现接口覆盖：作品章节、章节共创会话、带待决对焦和可选 `replyControl` 的会话消息、回复深度分层偏好、章节 Brief 状态/追加/确认/来源查询/异步收束、章节大纲读取/保存/调整候选创建/查询/放弃/确认、章节生成创建/详情/最近预览/采纳/拒绝/重新生成、章节正文读取/保存，以及设定候选查询/确认/忽略、正式设定查询、伏笔查询/创建、章节摘要、关键事件、用户配置、模型状态与连接测试、AI 任务查询/取消/失败讨论回复重试和 Agent Run 当前状态查询。
- 大纲候选接口为：`POST /api/chapters/{chapterId}/outline/candidates`、`GET /api/chapters/{chapterId}/outline/candidates/latest`、`GET /api/chapters/{chapterId}/outline/candidates/{candidateId}`、`POST .../{candidateId}/abandon`、`POST .../{candidateId}/confirm`。候选状态为 `queued/running/ready/failed/canceled/abandoned/confirmed`；详情返回绑定 Brief、基础大纲快照、结构化候选内容、确定性差异、三维共识影响和确认后的正式大纲引用。
- 章节生成创建接口同步返回 `draft` 资源标识，本地生成完成后生成记录进入 `preview`、关联 `ai_tasks` 进入 `succeeded`；生成器通过 `ChapterContentGenerator` 接口隔离，当前实现根据章节标题、brief、大纲快照和生成参数确定性构造中文预览，不调用真实 LLM。
- 创建和重新生成响应中的 `gmtCreate` 以生成记录持久化后的重新查询结果为准，不依赖数据库默认时间自动回填到插入实体；最近预览查询在数据库侧按创建时间和 ID 倒序并 `LIMIT 1`，且只读取预览摘要字段。
- 大纲和生成只读取显式指定或数据库侧按状态限一查出的 latest confirmed Brief；没有 confirmed Brief 时返回 `CHAPTER_CONFIRMED_BRIEF_REQUIRED`。生成依据快照保存 `confirmedBriefId`、`confirmedBriefVersion` 和生成时的 Brief 内容，重新生成继续使用原快照，不重新猜测 latest。
- 生成稿仅在 `preview` 状态可首次采纳或拒绝；采纳支持 `replace` 和 `append`，已采纳记录重复请求直接返回当前结果，不会二次写入正文。重新生成会创建新的 generation/task，并保留原依据、合并本次反馈。
- Web 层将 `page=abc`、整数溢出等请求参数类型转换失败统一映射为 `BAD_REQUEST` 和 HTTP 400；候选状态竞争与 AI 任务取消竞争分别返回 `SETTING_CANDIDATE_CONFLICT`、`AI_TASK_STATE_CONFLICT` 和 HTTP 409。
- 当前主流程数据流为：作品/章节创建 -> 章节共创消息沉淀 -> brief 与大纲收束 -> 章节生成记录 -> 用户采纳后写回 `chapters.content` -> 更新章节摘要、关键事件、设定候选和伏笔线索。
- 章节正文以 `chapters.content` 作为唯一事实源；生成记录、brief、大纲和知识层记录均围绕章节正文提供过程记录或上下文辅助。
- 当前接口文档不覆盖：正式前端页面、真实 AI 自动抽取服务、角色状态快照、叙事线程、时间线、知识巡检、token 汇总、LLM 调用日志和独立 `suggestions` 接口。

## 数据库与持久化要点

- 当前数据库迁移由 `moqi-start/src/main/resources/db/migration` 下的 Flyway SQL 管理，当前有效版本为 V1-V15。
- 当前数据库结构说明统一看 `docs/2026-06-09-数据库设计.md`；迁移历史和设计调整记录统一看 `docs/数据库设计变更记录.md`。
- P0 主流程以 `works`、`chapters`、`chapter_conversations`、`chapter_conversation_messages`、`chapter_briefs`、`chapter_generations` 为已落库基础。
- 自 issue #18 起，新增数据库表默认使用 `id`、`gmt_create`、`gmt_modified` 作为基础字段；历史 V1-V3 中的 `created_at/updated_at` 通过增量迁移改名，不重写旧迁移。
- `chapter_outlines` 是正式章节大纲事实源，一章一条，使用 `outline_content JSON` 保存本章目标、场景、人物变化、节奏、约束和未决问题，并用 `revision` 支撑大纲业务修订冲突控制；`version` 与继承 `BaseEntity` 的通用 MyBatis-Plus 映射保持一致，`confirmed_brief_id` 固化本次大纲承接的已确认共识。`chapter_outline_candidates` 保存候选任务、会话/Brief、不可变基础快照、候选内容、差异、共识影响和确认结果，候选不作为正式大纲事实源。
- `chapter_briefs` 是章节共创收束历史；`draft` 允许继续讨论和修改，只有用户通过确认接口产生的 `confirmed` 才能进入大纲和正文生成。结构化 V1 与历史自由文本继续共用 `brief_content LONGTEXT`。
- `user_configs` 是用户级通用配置表，首版用于承载模型配置、写作偏好、外观和同步配置；暂不单独设计 `model_providers`。
- `user_configs` 的首次创建从缺失态版本 `0` 推进到版本 `1`，并依靠用户、配置键和软删除标记的唯一约束阻止并发创建覆盖；后续更新使用当前行 `version` 作为条件执行原子更新；配置值使用结构化 JSON 解析和序列化。
- `ai_tasks` 承载 AI 回复、共识收束、正文生成和大纲调整候选等异步任务状态，供轮询和取消接口使用；`context_snapshot_id` 追溯实际模型上下文，`task_input_json` 保存可恢复 ID 引用，`result_brief_id` 与 `result_outline_candidate_id` 分别保存共识和候选任务结果。
- 三级故事规划使用 `work_narrative_plan_versions`、`chapter_plan_versions` 和 `scene_plan_versions`。场景候选固定当前作品规划和章节大纲 revision，经 `scene_plan_generation` Agent Run 生成并等待人工处理；模型输出必须满足章节摘要、`planned/disabled` 场景状态和从 1 开始的连续 sequence 约束。Provider、JSON、结构校验或持久化失败会以安全错误码同步到步骤、Run、AI Task，并将尚未就绪的候选收敛为 `failed`；发布前重新校验来源版本，已发布版本保持只读历史，`PublishedScenePlanQueryPort` 可按当前或明确版本读取有序 ScenePlan。
- `setting_candidates` 是 `setting_entries.source_candidate_id` 的外键父表；候选确认事务必须先锁定候选行，再写入或更新正式设定，最后按锁定快照的 `pending/version/deleted` 条件更新候选状态。
- 自 issue #18 的后续迁移起，P0 主流程相关表统一补充中文表注释和字段注释，便于通过数据库工具直接理解表语义。
- 当前 P0 数据库不保留 `biz_id` 业务唯一 ID 列，统一使用自增 `id` 作为主键和关联键。
- issue #22 起，数据库补充长篇小说知识层最小结构：`setting_candidates` 保存待确认设定，`setting_entries` 保存正式作品级设定，`foreshadowing_items` 保存伏笔与线索，`chapter_summaries` 保存章节摘要，`chapter_key_events` 保存章节关键事件。
- `chapters.chapter_type` 用于区分 `dedication`、`prologue`、`chapter`、`epilogue`、`other`，导入既有小说时应保留献词、序幕、尾声等非标准正文块。

## 运行与脚本说明

- `application.yml` 继续设置 `spring.ai.model.chat=none`，禁止 Spring Boot 根据静态属性自动创建默认 ChatModel Bean。DeepSeek Provider 由业务服务在连接测试或后续模型调用时按数据库配置显式创建，因此修改配置无需重启，也不会复用旧 Key 客户端。
- 凭据主密钥仅从 `MOQI_CREDENTIAL_ACTIVE_KEY_ID` 与 `MOQI_CREDENTIAL_KEYS` 读取；后者使用逗号分隔的 `keyId=Base64AES256Key`。当前写入使用 active key，历史 key 保留在 key ring 中供解密和轮换，主密钥不得写入 Git、数据库、日志或接口响应。
- 应用启动后扫描 `model.active` 旧明文 `apiKey`；发现旧明文时在单事务内写入凭据并以配置版本 CAS 清除原字段。主密钥不可用、配置畸形或 CAS 冲突时启动失败并整体回滚。
- 本地 MySQL 默认使用 `E:\middleware\mysql-8.4.9`，连接配置见 `moqi-start/src/main/resources/application-local.yml`。
- `scripts/start-local-mysql.ps1` 用于启动本地 MySQL，`scripts/stop-local-mysql.ps1` 用于停止本地 MySQL。
- `scripts/import-longzu-i.ps1` 用于将 `E:\books\龙族ⅰ-火之晨曦.txt` 按分隔线标题块导入 `moqi_dev`，写入作品、章节、章节大纲、章节简报、导入稿记录、设定、伏笔、章节摘要和关键事件。
- `scripts/verify-longzu-i-import.ps1` 用于从数据库按 `chapter_no` 还原《龙族Ⅰ-火之晨曦》的标题、章节类型和正文，并统计章节主流程表与知识层记录，验证导入是否完整。

- 章节正文保存和生成稿采纳要求客户端提交 `baseVersion`；版本冲突返回 HTTP 409 和 `CHAPTER_VERSION_CONFLICT`，`data` 包含 `serverContent`、`version`、`serverSavedAt`。当前章节生成使用确定性本地实现，尚未接入真实模型、后台执行器或流式输出。

## Agent Runtime 技术验证边界

- Issue #43 已将 Spring AI Alibaba Graph Core `1.1.2.2` 接入 `moqi-service` 的内部适配层；Graph 类型仅位于 `agent.infrastructure`，业务 Service、Controller、SSE 和持久化契约不依赖框架类型。Graph Core 的无关数据库、RAG、Redisson、Mongo、MCP 与 Commons Exec 传递依赖被排除；其静态序列化器强制链接的 ZhiPuAI 类保留为二进制依赖，但未启用任何 ZhiPuAI Provider。
- `AgentRuntime` 提供启动、按用户读取、恢复、恢复令牌重签、单步重试和取消端口；`agent_runs`、`agent_run_steps`、`agent_checkpoints`、`agent_interruptions` 分别保存多步骤状态、尝试记录、版本化 JSON checkpoint 和人工恢复令牌哈希。幂等键绑定完整启动请求，人工恢复从 checkpoint 的下一步骤继续，并把校验后的确认内容作为后续步骤输入。`GET /api/agent-runs/{runId}` 仅用于 SSE 断线后读取持久化事实，当前按固定用户 `local-user` 校验归属，不暴露 checkpoint 内容或恢复 token；通用工作流启动、恢复和取消仍由后续具体小说工作流通过内部端口接入。恢复语义见 `docs/Agent Runtime 恢复语义.md`。
- 技术决策为部分采用：后续可在内部适配层使用 Graph Core 的编排能力，但业务 Service、SSE 和领域模型不得依赖框架类型。
- Spring AI Alibaba `1.1.2.2` 内置 `MysqlSaver` 的 checkpoint 缺少稳定单调顺序，同秒多 checkpoint 的重启恢复存在非确定性；生产实现不得直接采用该 Saver 或其 Java 对象序列化载荷。
- 后续生产 checkpoint 必须使用 Moqi 自有、可版本化的 JSON 契约和确定性 sequence，并以数据库条件更新保证确认、取消和 resume 幂等。详细证据、退出条件和备选状态机见 `docs/adr/ADR-0001-Spring-AI-Alibaba-Graph-运行时技术验证.md`。

## 场景小说生成恢复边界

作品叙事规划除当前发布版外，还可通过 `GET /api/works/{workId}/narrative-plans/latest-draft` 恢复最新草稿；不存在草稿时返回空数据，不以异常代替空状态。

逐场景生成以 `chapter_generations`、`chapter_generation_scenes`、`agent_runs` 与 `agent_run_steps` 为事实源。场景读取返回持久化候选正文、当前重试 attempt、可重试标记和安全错误摘要。运行步骤失败会把对应运行中场景写为 `failed` 并发布 `generation.scene.failed`；取消场景为 `canceled`，不允许重试。前端 SSE 重连或刷新后必须重新读取持久化资源，不得依赖内存中的增量文本。
